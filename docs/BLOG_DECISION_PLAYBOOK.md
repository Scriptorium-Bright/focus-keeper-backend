# RebootFocus Blog Decision Playbook

> Version: v0.1  
> Updated: 2026-03-16  
> Scope: 블로그에 남길 의사결정 글을 어떤 Phase에서, 어떤 주제로, 언제 쓰면 좋은지 정리한 운영 기준

## 1. 목적

- 이 문서는 "어떤 Phase에서 어떤 의사결정을 블로그로 남길 것인가"를 정리한 플레이북이다.
- 포트폴리오는 결과물을 보여주는 문서이고, 블로그는 판단 과정을 길게 설명하는 문서라는 점을 분리한다.
- 개발 중에 좋은 의사결정이 묻히지 않도록, Phase별 블로그 후보와 작성 타이밍을 미리 정해둔다.

## 2. 기본 원칙

- 블로그 글은 기능 소개보다 `판단의 이유`가 먼저 나와야 한다.
- 글 하나는 가능하면 질문 하나에 답하는 구조로 쓴다.
- 구현 중간보다는 `Phase 종료 검토 직후`에 쓰는 것이 좋다.
- 테스트, 로그, 지표, 다이어그램 중 최소 1개 이상 증빙이 있을 때 쓴다.
- 아직 판단이 열려 있는 주제는 "최종 결론"보다 "왜 이렇게 생각이 바뀌었는가" 중심으로 쓴다.

## 3. 언제 쓰는가

가장 좋은 타이밍은 아래 두 시점이다.

### 3.1 Phase Exit 직후

- 해당 Phase의 P0 기능이 끝났고
- `docs/refactor.md`에 High / Mid / Low가 정리됐고
- `문제 -> 해결 -> 결과` 초안이 적혔을 때

이 시점은 글의 구조가 가장 잘 나온다.  
왜냐하면 구현이 끝나서 증빙이 생겼고, 아직 판단 이유를 생생하게 설명할 수 있기 때문이다.

### 3.2 방향 전환 직후

- ICP 변경
- Phase 우선순위 재정의
- 메시징/아키텍처 전략 변경
- KPI 재정의

이런 변화는 특정 기능이 없어도 글이 된다.  
오히려 "왜 생각이 바뀌었는가"를 설명하는 좋은 주제다.

## 4. 어떤 글이 좋은가

좋은 블로그 글은 아래 구조를 가진다.

1. 문제
2. 기존 생각 또는 대안
3. 선택한 방향
4. 왜 그렇게 선택했는가
5. 구현 또는 검증 결과
6. 남은 리스크

한 줄로 말하면 `기능 소개 글`이 아니라 `의사결정 설명 글`이어야 한다.

## 5. Phase별 블로그 우선순위

### 5.1 꼭 쓰면 좋은 Phase

이 Phase들은 블로그 소재로 강하다.

- Phase 2
  - 공통 응답/예외/트레이스 표준화
- Phase 4
  - 복귀 도메인 모델링, 상태 전이, 실패 reason taxonomy
- Phase 5
  - 실패 직후 10분 복귀 재시작 설계
- Phase 11
  - KPI 집계, ETL, 신뢰 가능한 지표 설계
- Phase 13
  - 복귀 마찰 분석, 시간대별 실패 분포, friction signal
- Phase 14
  - 관측성, 알림, 룬북
- Phase 15
  - AI를 코어 경로에서 분리하는 구조

### 5.2 선택적으로 쓰면 좋은 Phase

- Phase 3
  - 온보딩을 뒤로 미루고 복귀 루프를 먼저 구현한 우선순위 판단
- Phase 6
  - Rule-based retrospective를 AI보다 먼저 둔 이유
- Phase 7
  - 복귀 리마인더를 언제 보내는지에 대한 판단
- Phase 8
  - Billing foundation의 최소 구조
- Phase 9
  - 실험 인프라를 어떻게 설계했는지
- Phase 10
  - 단일 ICP 메시지와 성장 루프

### 5.3 굳이 쓰지 않아도 되는 Phase

- Phase 1
  - 부트스트랩 자체는 글 소재가 약함
- Phase 12
  - 차별점보다 후순위 기능이라면 블로그 우선순위가 낮음

## 6. Phase별 권장 블로그 주제

| Phase | 추천 글 제목 방향 | 핵심 질문 | 글을 쓰기 좋은 시점 | 필요한 증빙 |
|---|---|---|---|---|
| 2 | 왜 먼저 공통 응답/예외/트레이스를 고정했는가 | 기능보다 API 일관성을 먼저 잡은 이유는? | Phase 2 종료 직후 | 테스트, 에러 응답 예시 |
| 3 | 왜 온보딩보다 복귀 루프를 먼저 만들었는가 | 제품 차별점이 없는 온보딩을 왜 미뤘는가 | 방향 전환 직후 또는 Phase 3 종료 시 | 우선순위 변경 기록 |
| 4 | 복귀 앱의 핵심은 타이머가 아니라 상태 전이였다 | Timebox, Session, Failure를 왜 분리했는가 | Phase 4 종료 직후 | 통합 테스트, 도메인 모델 |
| 5 | 실패 직후 10분 재시작을 어떻게 설계했는가 | 재시작 제안을 언제, 어떤 규칙으로 띄울 것인가 | Phase 5 종료 직후 | E2E 테스트, 시퀀스 다이어그램 |
| 6 | 왜 AI보다 Rule-based 회고를 먼저 만들었는가 | 복잡한 추천보다 단순 규칙을 먼저 둔 이유는? | Phase 6 종료 직후 | 회고 규칙, 샘플 출력 |
| 7 | 복귀 리마인더는 언제 보내야 하는가 | 하루 중 어느 시점이 복귀에 더 효과적인가 | Phase 7 종료 직후 | 알림 로그, 실패 시간대 분석 |
| 8 | Billing은 얼마나 늦게, 얼마나 단순하게 넣어야 하는가 | 복귀 제품에서 결제를 최소 구조로 두는 이유는? | Phase 8 종료 직후 | 권한 모델, 플로우 다이어그램 |
| 9 | 실험 인프라는 왜 기능보다 늦게 들어가는가 | Paywall/Trial 실험을 어떤 기준으로 설계했는가 | Phase 9 종료 직후 | 실험 이벤트 스키마 |
| 10 | 넓은 성장보다 단일 ICP 메시지가 먼저인 이유 | 왜 한 세그먼트에만 집중했는가 | Phase 10 종료 직후 | 랜딩 문구, 진단 결과 |
| 11 | 신뢰할 수 있는 Recovery24를 만들기 위해 필요한 것들 | KPI는 왜 raw/clean/mart와 DQ가 필요한가 | Phase 11 종료 직후 | ETL, backfill, DQ |
| 13 | 사용자는 왜 특정 시간대에 더 자주 실패할까 | 실패 시간대/반복 실패 패턴을 어떻게 읽는가 | Phase 13 종료 직후 | failure hour mart, signal report |
| 14 | 운영은 기능이 아니라 시스템 신뢰의 문제였다 | 대시보드, 알림, 룬북을 왜 분리했는가 | Phase 14 종료 직후 | 메트릭, 알림, 룬북 |
| 15 | AI는 코어 경로 밖에 둬야 했다 | 왜 AI 회고를 완전 비동기로 분리했는가 | Phase 15 종료 직후 | 큐/워커 구조, timeout/fallback |

## 7. 지금 프로젝트 기준 추천 순서

지금 이 프로젝트에서 블로그를 쓰기 좋은 순서는 아래와 같다.

1. Phase 4
   - 이유: 이미 구현 증거가 있고, 도메인 모델링 이야기가 선명하다.
2. Phase 5
   - 이유: 제품 차별점이 가장 잘 드러난다.
3. Phase 11
   - 이유: 데이터 엔지니어링 포지션과 직접 연결된다.
4. Phase 14
   - 이유: 운영 역량을 보여주기 좋다.
5. Phase 15
   - 이유: AI를 어떻게 분리했는지 설명력이 높다.

보조 글로는 아래가 좋다.

- ICP를 왜 이렇게 좁혔는가
- 왜 뽀모도로 앱처럼 보이지 않게 만들었는가
- 왜 온보딩을 뒤로 미뤘는가

## 8. 글 하나를 쓰기 전에 확인할 것

- [ ] 질문 하나에 답하는 글인지
- [ ] `문제 -> 선택 이유 -> 결과` 구조가 되는지
- [ ] 코드/테스트/지표/다이어그램 중 최소 1개 증빙이 있는지
- [ ] 아직 미정인 내용을 확정된 것처럼 쓰지 않는지
- [ ] 포트폴리오와 겹치더라도 블로그는 판단 이유 중심으로 차별화했는지

## 9. 블로그와 포트폴리오의 차이

### 포트폴리오

- 짧고 구조적이어야 한다.
- 결과와 증빙이 먼저 보여야 한다.
- 면접관이 빠르게 훑을 수 있어야 한다.

### 블로그

- 판단 과정과 시행착오를 더 길게 설명할 수 있다.
- 왜 이 대안을 버렸는지까지 쓸 수 있다.
- 문제 정의와 선택 기준을 더 깊게 풀 수 있다.

즉 같은 소재라도 포트폴리오는 압축본, 블로그는 확장본에 가깝다.

## 10. 권장 운영 방식

- 각 Phase 종료 시 `docs/refactor.md`를 먼저 정리한다.
- 그다음 `docs/decision-log.md`에서 해당 주제의 변화 과정을 확인한다.
- 이후 이 문서 기준으로 블로그 후보를 고른다.
- 블로그 초안은 아래 포맷으로 시작한다.

```text
[제목]
[문제]
[이전 생각 또는 대안]
[선택한 방향]
[선택 이유]
[구현/검증 결과]
[남은 리스크]
```
