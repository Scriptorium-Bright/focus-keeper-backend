# Global Expansion Playbook (Validation-First)

> Version: v0.2  
> Updated: 2026-03-12  
> Scope: RebootFocus의 글로벌 확장 가능성을 저비용/단기 실험으로 검증하기 위한 실행 문서

## 1. 목적

- "글로벌 출시"가 아니라 "글로벌 검증"을 먼저 수행한다.
- 감이 아니라 KPI/비용/운영 안정성 수치로 Go/No-Go를 결정한다.
- 채용 포트폴리오 관점에서 글로벌 실험 설계/운영 역량을 증명한다.

## 2. 핵심 가설

- 가설 A: 실패 후 재시작 문제는 국가를 넘어 공통으로 존재한다.
- 가설 B: RebootFocus 실행 루프(Brain Dump -> Big3 -> Timeboxing -> Re-timeboxing)는 다국어 환경에서도 유지된다.
- 가설 C: 저비용 AI 모델 조합으로도 회고/코칭 품질을 실용 수준으로 맞출 수 있다.

## 3. 실행 원칙

- Validation First: 글로벌 진출 판단 전에 6주 검증을 완료한다.
- Cost Guardrail: 사용자당 AI 비용 상한을 정하고 초과 시 자동 downgrade/fallback한다.
- Localized UX: 언어 번역만이 아니라 시간대/날짜/문화권 표현을 로컬에 맞춘다.
- Evidence-driven: 모든 결정은 실험 리포트와 대시보드 근거로 남긴다.

## 4. 우선 타깃 시장 (Phase 0)

- KR(기준군): 기존 사용자군
- EN(영어권 소규모): 제품 메시지/행동 루프의 일반성 확인
- VN(베트남권 소규모): 아시아권 확장성 확인

선정 이유:
- 비용 대비 빠른 학습 가능
- 한국 기준군과 비교가 쉬움
- 아시아 확장 스토리텔링에 적합

## 5. 6주 실행 계획

### 5.1 Week 1-2 (2026-03-11 ~ 2026-03-24)

- i18n 최소 지원: `ko`, `en` (필수), `vi`(가능 범위)
- timezone/locale 처리 점검
- KPI 대시보드에 국가 차원 추가
- AI 프롬프트 템플릿 분리(언어별)
- 모델 라우팅 정책 초안 구축(저비용 우선)

### 5.2 Week 3-4 (2026-03-25 ~ 2026-04-07)

- 소규모 베타 모집:
  - KR 30명
  - EN 30명
  - VN 20~30명
- 이벤트 로깅/품질 점검
- 주간 회고 생성 품질 샘플 평가(언어별)

### 5.3 Week 5-6 (2026-04-08 ~ 2026-04-21)

- 지역별 KPI 비교 분석

- 운영 이슈(장애, 누락, CS) 정리

## 6. 측정 KPI

- Activation(24h)
- Recovery24 (메인)
- Recovery48 (보조)
- RestartCount24/48
- TTR
- CycleCompletionRate
- PlanExecutionRate
- D7 Retention
- 주간 회고 열람률
- AI 응답 평균 지연
- 사용자당 AI 비용

### 6.1 Recovery Metric Pack (정의 고도화)

- 복귀 여부:
  - `Recovery24`: 실패 후 24시간 내 1회 이상 재시작 여부
  - `Recovery48`: 실패 후 48시간 내 1회 이상 재시작 여부
- 복귀 강도:
  - `RestartCount24`: 실패 후 24시간 내 재시작 횟수
  - `RestartCount48`: 실패 후 48시간 내 재시작 횟수
- 복귀 속도:
  - `TTR`: 실패 시점부터 첫 재시작까지 걸린 시간
- 집중 사이클:
  - `CycleStarted`: 집중-휴식 사이클 시작 횟수
  - `CycleCompleted`: 집중-휴식 사이클 완료 횟수
  - `CycleCompletionRate`: `CycleCompleted / CycleStarted`
- 품질 보정:
  - 3분 미만 짧은 재시작은 스팸성 이벤트로 분리 집계
  - 횟수 지표는 완료율/실집중시간과 함께 해석

### 6.2 실무 해석 규칙

- `Recovery24`는 실행 복구력의 메인 KPI로 사용한다.
- `Recovery48`은 롱테일 복귀 회수율 확인용 보조 KPI로 사용한다.
- 재시작 횟수만 단독으로 사용하지 않고 `CycleCompletionRate`, `EffectiveFocusMinutes`와 함께 본다.

## 7. Go / No-Go 기준 (초안)

- Go:
  - KR 대비 EN/VN의 Recovery24, D7이 임계치 내(예: KR 대비 80% 이상)
  - Recovery48, TTR, CycleCompletionRate가 하락/악화 추세가 아님
  - 사용자당 AI 비용이 상한 이하
  - 운영 장애가 통제 가능 수준
- Hold:
  - KPI는 유망하지만 비용/운영 이슈가 큰 경우
  - 시장 확장보다 파이프라인/모델 최적화를 우선
- No-Go:
  - 핵심 KPI가 반복적으로 임계치 미달
  - 비용 구조가 단기 개선 불가

## 8. AI 모델/비용 전략

- 기본 정책:
  - 경량 모델 우선(예: Flash/Gemma 계열)
  - 실패/저품질 시 상위 모델 fallback
- 프롬프트 운영:
  - 언어별 시스템 프롬프트 분리
  - AI에게 프롬프트 개선안을 생성시키고 A/B 평가
- 비용 제어:
  - 토큰 상한
  - 응답 길이 제한
  - 캐시 가능한 템플릿 응답 재사용

## 9. 데이터 파이프라인 요구사항

- 국가/언어/시간대 메타데이터를 이벤트에 포함
- Airflow DAG에서 국가별 KPI 파티션 집계
- Recovery Metric Pack 수식은 `docs/spec/RECOVERY_METRICS.md` 기준 사용
- 데이터 품질 체크:
  - locale 누락률
  - 국가별 이벤트 유실률
  - 지연 p95

## 10. 리스크와 대응

- 번역 품질 저하:
  - 핵심 UX 문구 우선 수동 검수
- 문화적 맥락 불일치:
  - 지역별 인터뷰/피드백 루프
- 비용 급증:
  - 모델 downgrade + 생성 빈도 제한
- 운영 복잡도 증가:
  - 국가 확장을 1개씩 순차 적용

## 11. 산출물 (포트폴리오/지원서 활용)

- 글로벌 검증 실험 설계서
- 국가별 KPI 대시보드 캡처
- 비용 최적화 리포트
- Go/No-Go 의사결정 문서

## 12. 다음 액션 (즉시)

1. 국가/언어 이벤트 스키마 확정
2. 모델 라우팅 정책(기본/대체) 확정
3. 1차 베타 모집 기준 및 채널 확정
4. 주간 리포트 템플릿 생성

## 13. Execution Method (5-Step)

아래 5단계를 순서대로 적용한다.

1. 요구사항에 의문 제기:
   - "48시간 내 재시작" 문구를 그대로 쓰지 않고, `Recovery24`(메인) + `Recovery48`(보조)로 재정의
2. 불필요한 과정 삭제:
   - 의미가 약한 단일 횟수 지표를 제거하고, 핵심 지표 팩으로 단순화
3. 단순화/최적화:
   - `복귀 여부/강도/속도/사이클` 4축으로 정리해 대시보드 해석 복잡도 축소
4. 사이클 타임 가속:
   - Week 단위로 KPI 수집 -> 리포트 -> 문구/UX 수정 루프를 고정
5. 자동화는 마지막:
   - 먼저 지표 정의/품질 보정 확정 후 Airflow/Kafka 자동화를 단계적으로 적용
