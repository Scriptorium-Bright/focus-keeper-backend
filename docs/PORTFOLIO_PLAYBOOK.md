# RebootFocus Portfolio Playbook

> Version: v0.2  
> Updated: 2026-03-16  
> Scope: 취업용 포트폴리오를 기능 설명서가 아니라 문제 해결 문서로 만드는 기준

## 1. 목적

- 이 문서는 "어떻게 포트폴리오를 보여줄 것인가"에 대한 기준선이다.
- 프로젝트 설명을 기능 목록 중심이 아니라 문제 해결 스토리 중심으로 정리한다.
- 채용 제출물, 발표 자료, 프로젝트 소개 문서가 같은 메시지를 유지하도록 돕는다.

## 2. 피해야 할 방식

잘못된 포트폴리오 예:
- 제목
- 목차
- 인적사항
- 기능 캡처
- 기능 설명 나열

왜 안 좋은가:
- 기능 구현은 이미 기본 역량으로 간주되는 경우가 많다.
- 기능 목록만으로는 사고력, 문제 해결력, 우선순위 판단을 보여주기 어렵다.
- 면접관 입장에서 "무엇을 만들었나"보다 "왜 그렇게 풀었나"가 더 중요하다.

## 3. 면접관이 보고 싶은 것

포트폴리오의 핵심은 기능 설명이 아니라 `Problem Solving Story`다.

반드시 드러나야 하는 것:
- 어떤 문제가 있었는지
- 왜 그 문제가 중요했는지
- 어떤 대안을 검토했는지
- 왜 그 해결책을 선택했는지
- 결과를 어떻게 검증했는지

## 4. 기본 구성 원칙

각 사례는 아래 3단 블록으로 정리한다.

1. 문제 상황
2. 해결 방법
3. 결과

권장 길이:
- 각 블록 2~3줄
- 수치/로그/테스트 결과 최소 1개 포함

## 5. 합격 구조 (권장 제출 순서)

취업용 포트폴리오는 아래 순서로 정리한다.

1. 한 페이지 프로젝트 요약 (`Project Overview`)
2. 문제 정의 (`Problem`)
3. 시스템 설계 (`Architecture`)
4. 핵심 문제 해결 (`Core Challenges`)
5. 기술적 의사결정 (`Tech Decisions`)
6. 성능/개선 (`Improvement`)
7. 배운 점 (`Lessons`)

원칙:
- 첫 페이지에서 면접관이 30초 안에 프로젝트를 이해할 수 있어야 한다.
- `Core Challenges`가 포트폴리오의 중심이고, 기능 소개는 이 안에 흡수한다.
- `Tech Decisions`와 `Improvement`는 구현 자랑이 아니라 판단 근거와 결과를 보여주는 섹션이다.

## 6. 반드시 포함하면 좋은 시각 자료

- 아키텍처 다이어그램
- 데이터 플로우 다이어그램
- 시퀀스 다이어그램
- KPI 흐름도 또는 ETL 흐름도

원칙:
- "예쁘게 보이는 그림"보다 "왜 이 구조가 필요한지 설명되는 그림"이어야 한다.
- 그림 1장당 메시지는 1개만 담는다.

## 7. 한 페이지 프로젝트 요약 작성법

첫 페이지에는 아래 5개만 넣는다.

- 프로젝트 한 줄 설명
- 해결하려는 문제
- 사용 기술
- 전체 아키텍처 요약
- 핵심 기능 3~4개

예시 템플릿:

```text
[프로젝트명]
[한 줄 설명]

[문제]
- ...

[Tech]
- ...

[Architecture]
- Client -> API -> DB -> Batch -> KPI Mart

[핵심 기능]
- ...
- ...
- ...
```

RebootFocus 초안 예시:

```text
RebootFocus
전날 계획이 무너지면 다음날까지 다시 못 붙잡는 직장인을 위해, 놓친 일을 다시 시작하게 만드는 복귀 코치 백엔드

문제
- 생산성 앱은 많지만 "실패 다음날 다시 시작"을 구조적으로 돕는 제품은 드물다.
- 사용자가 전날 실패하면 다음날 첫 집중 블록을 다시 못 잡고 루프에서 이탈한다.

Tech
- Spring Boot / Java / PostgreSQL / Spring Batch / Docker

Architecture
- Client -> Recovery API -> PostgreSQL -> Batch -> KPI Mart -> Dashboard

핵심 기능
- Brain Dump / Big3 / 첫 복귀 블록 배정
- 실패 체크인과 10분 복귀 재시작
- Recovery24 / TTR KPI 집계
- 복귀 마찰 신호 및 운영 관측
```

## 9. 섹션별 작성 기준

### 9.1 Problem

- 실제 사용자의 불편이나 운영상의 비효율을 짧고 선명하게 적는다.
- "왜 이 문제가 중요한가"를 함께 적는다.
- 가능하면 현실 맥락을 넣는다.

### 9.2 Architecture

- 전체 구조를 한 장으로 보여준다.
- 시스템 경계, 데이터 저장 위치, 동기/비동기 분리를 드러낸다.
- 그림 아래에는 "왜 이 구조가 필요한가"를 2~3줄로 덧붙인다.

### 9.3 Core Challenges

- 2~4개만 고른다.
- 각 챌린지는 `문제 -> 접근 -> 해결 -> 결과` 순서로 적는다.
- 여기서 기능 설명은 보조적이어야 하고, 핵심은 문제 해결 흐름이다.

### 9.4 Tech Decisions

- "왜 Spring Boot인가", "왜 RDB인가", "왜 Batch SQL부터 시작했는가" 같은 질문에 답한다.
- 후보 대안과 선택 이유를 함께 적는다.
- 기술 선택은 유행보다 도메인 적합성과 운영 현실을 기준으로 설명한다.

### 9.5 Improvement

- 성능, 안정성, 품질 개선 사례를 넣는다.
- 예: 충돌 검증, 인덱스, 멱등 upsert, 재처리, DQ, 알림 기준
- 수치가 없으면 개선 섹션으로 취급하지 않는다.

### 9.6 Lessons

- "무엇을 배웠는가"보다 "다음에는 무엇을 다르게 할 것인가"가 보이게 적는다.
- 초기 데이터 모델, 이벤트 설계, 범위 조절, 온보딩 우선순위 같은 판단의 교훈을 남긴다.

## 10. RebootFocus에 맞는 포트폴리오 사례 유형

### 10.1 복귀 루프 설계 사례

- 문제: 사용자가 전날 실패하면 다음날 첫 복귀 블록을 다시 못 잡는다.
- 해결: Brain Dump -> Big3 -> Timebox -> Failure Check-in -> Restart로 복귀 루프를 구조화한다.
- 결과: Recovery24, TTR, RestartCount로 검증한다.

### 10.2 데이터 파이프라인 사례

- 문제: 복귀 KPI는 이벤트가 쌓여도 신뢰성 있게 집계되지 않으면 의미가 없다.
- 해결: raw/clean/mart, 워터마크, 멱등 upsert, 백필, DQ를 적용한다.
- 결과: `daily_kpi_pipeline`, 재처리 로그, DQ 지표로 검증한다.

### 10.3 운영/관측 사례

- 문제: 핵심 복귀 경로 장애가 배치/AI 장애와 섞이면 원인 파악이 늦어진다.
- 해결: 동기 경로와 비동기 경로를 분리하고, 메트릭/알림/룬북을 표준화한다.
- 결과: 대시보드, 알림 기준, 장애 대응 시간으로 설명한다.

## 11. 이 프로젝트에서 권장하는 포트폴리오 패킷

- 1장: 한 페이지 프로젝트 요약
- 1장: 문제 정의
- 1장: 전체 아키텍처
- 2~4장: 핵심 문제 해결 사례
- 1장: 기술적 의사결정
- 1장: 성능/운영/데이터 개선
- 1장: 배운 점과 다음 우선순위

상세 템플릿은 `docs/PORTFOLIO_PACKET_TEMPLATE.md`를 따른다.

## 12. 금지 규칙

- 기능 캡처만 나열하지 않는다.
- "많이 만들었다"를 성과로 포장하지 않는다.
- 수치 없는 개선 주장을 하지 않는다.
- 본인이 하지 않은 일을 확대 해석하지 않는다.
