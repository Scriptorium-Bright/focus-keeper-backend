# RebootFocus Phase Exit Protocol

> Version: v0.1  
> Updated: 2026-03-16  
> Scope: 각 Phase 종료 시점에 어디서 멈추고 무엇을 기록할지 고정하는 기준

## 1. 목적

- 이 문서는 "언제 다음 Phase로 넘어가도 되는가"를 정하는 종료 프로토콜이다.
- 구현을 계속 밀어붙이다가 포트폴리오 증빙과 리팩터 우선순위를 놓치지 않도록 한다.
- 각 Phase를 `문제 -> 해결 -> 결과` 구조로 정리할 수 있는 멈춤 지점을 명시한다.

## 2. 기본 원칙

- `N.x`는 구현 단위다.
- `Phase`는 멈춰서 정리하는 단위다.
- 각 `N.x` 종료 시에는 테스트와 커밋을 한다.
- 각 `Phase` 종료 시에는 반드시 한 번 멈춰서 아래 4개를 정리한다.
- 각 `Phase` 종료 시에는 반드시 한 번 멈춰서 아래 5개를 정리한다.
  - High / Mid / Low 리팩터 항목
  - 포트폴리오 적용 가능 사례
  - 블로그로 확장할 수 있는 의사결정 주제
  - 문제 / 해결 / 결과 초안
  - 다음 Phase 진입 허용 여부

## 3. 언제 멈출 것인가

다음 4개가 충족되면 Phase 종료 검토를 위해 멈춘다.

1. 해당 Phase의 P0 `F-00x`가 모두 `done` 또는 명시적 제외 상태다.
2. 해당 Phase 핵심 플로우의 테스트가 통과한다.
3. 적어도 1개의 증빙이 생겼다.
   - 테스트 결과
   - KPI/로그
   - 재처리 결과
   - 다이어그램
4. 다음 Phase로 넘어가기 전에 수정해야 할 위험이 무엇인지 설명 가능하다.

즉, "기능이 대충 돌아간다"가 아니라 "이 Phase의 문제를 이렇게 풀었고, 남은 위험이 이것이다"라고 말할 수 있을 때 멈춘다.

## 4. Phase 종료 체크리스트

### 4.1 기술 종료 체크

- [ ] 해당 Phase의 핵심 `F-00x` 구현 완료
- [ ] 정상/예외 테스트 통과
- [ ] API 계약/스펙/체크리스트 동기화
- [ ] 관측 또는 KPI 포인트 연결 여부 확인

### 4.2 리팩터 분류 체크

- [ ] `High`: 다음 Phase 시작 전 반드시 고쳐야 할 항목 정리
- [ ] `Mid`: 다음 1~2개 Phase 내에 해결할 항목 정리
- [ ] `Low`: 당장 막지는 않지만 품질상 남겨둘 항목 정리

### 4.3 포트폴리오 체크

- [ ] 이번 Phase에서 포트폴리오에 쓸 사례 1개 이상 선택
- [ ] 사례를 `문제 -> 해결 -> 결과` 3블록으로 적기
- [ ] 증빙 1개 이상 연결
- [ ] 추천 시각 자료 1개 이상 연결

### 4.4 블로그 체크

- [ ] 이번 Phase에서 블로그로 풀 수 있는 의사결정 1개 이상 선택
- [ ] 글 제목이 아니라 "질문" 형태로 쓸 수 있는지 확인
- [ ] 왜 이 선택을 했는지와 버린 대안이 설명 가능한지 확인
- [ ] 테스트/지표/다이어그램 중 최소 1개 증빙이 있는지 확인

### 4.5 다음 Phase 진입 체크

- [ ] 현재 `High` 항목이 다음 Phase를 막는지 판정
- [ ] 막는다면 다음 Phase 진입 보류
- [ ] 막지 않는다면 다음 Phase의 첫 `F-00x`만 착수

## 5. 문제 -> 해결 -> 결과로 나오게 하는 방법

각 Phase 종료 시 아래 포맷을 채운다.

```text
[문제]
- 사용자가/운영이/데이터가 무엇 때문에 손실을 봤는가

[해결]
- 어떤 구조, 정책, 설계 결정으로 그 문제를 줄였는가

[결과]
- 테스트, 지표, 로그, 재처리 결과 중 무엇으로 확인했는가

[남은 리스크]
- 다음 Phase 전에 꼭 고칠 것인지, 나중에 미뤄도 되는지
```

이걸 못 쓰면 아직 멈출 시점이 아니다.  
이걸 쓸 수 있으면 다음 Phase로 넘어가기 전에 반드시 문서에 남긴다.

## 6. 현재 프로젝트에 적용하는 멈춤 지점

### Phase 4

- 멈춤 시점:
  - `F-003 Timebox`
  - `F-004 Recovery Session`
  - `F-005 Failure Check-in`
  - 위 3개 테스트 통과 후
- 종료 시 기록:
  - 첫 복귀 블록 충돌 정책
  - 세션 상태 전이 충돌 정책
  - 실패 체크인 reason taxonomy
  - `C-01` 사례의 `문제 -> 해결 -> 결과` 초안
  - 블로그 후보: "복귀 앱의 핵심은 타이머가 아니라 상태 전이였다"

### Phase 5

- 멈춤 시점:
  - `F-006 10분 복귀 재시작` 완료 후
  - 실패 -> 재시작 핵심 플로우 테스트 통과 후
- 종료 시 기록:
  - 재시작 제안 규칙
  - Recovery24 입력 이벤트 완전성
  - `C-01` 시퀀스 다이어그램 초안
  - 블로그 후보: "실패 직후 10분 재시작은 어떻게 설계했는가"

### Phase 11

- 멈춤 시점:
  - KPI mart, 코호트, 퍼널 중 P0 범위 완료 후
- 종료 시 기록:
  - DQ, 워터마크, 멱등 upsert, 백필 관련 `C-02`
  - 블로그 후보: "신뢰할 수 있는 Recovery24를 만들기 위해 필요한 것들"
